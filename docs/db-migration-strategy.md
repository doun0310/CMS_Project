# DB Migration Strategy

기준일: 2026-07-23

## 1. 목적

본 문서는 CMS Printer Application의 데이터베이스 변경을 안전하게 관리하기 위한 마이그레이션 전략을 정의한다.

## 2. 기본 원칙

- 스키마 변경은 모두 버전 관리한다.
- 운영 DB에는 수동 SQL 직접 반영을 지양한다.
- `forward-only` 원칙을 기본으로 한다.
- 파괴적 변경은 최소 2단계 이상으로 분리한다.

## 3. 권장 방식

초기 단계에서는 아래 중 하나를 선택한다.

1. SQL 파일 기반 마이그레이션
2. ORM/Query Tool 기반 마이그레이션

현재 프로젝트 상태를 고려하면 초기에는 `SQL 파일 기반 마이그레이션`이 가장 단순하다.

권장 디렉터리 예시:

```text
db/
  schema.sql
  seed.sql
  migrations/
    20260723_001_init.sql
    20260730_002_add_audit_indexes.sql
```

## 4. 파일 네이밍 규칙

권장 규칙:

`YYYYMMDD_순번_설명.sql`

예시:

- `20260723_001_init.sql`
- `20260724_002_add_template_status.sql`
- `20260731_003_update_print_job_indexes.sql`

## 5. 마이그레이션 절차

### 개발 환경

1. 로컬에서 신규 SQL 파일 작성
2. 빈 DB에 처음부터 적용 테스트
3. 기존 개발 DB에 순차 적용 테스트
4. 애플리케이션 동작 확인

### 검수/스테이징 환경

1. 개발 완료된 마이그레이션 순차 반영
2. 시드 데이터 필요 여부 검토
3. 핵심 API 회귀 테스트

### 운영 환경

1. 반영 전 백업
2. 반영 시간대 조율
3. 순차 마이그레이션 적용
4. 상태 확인
5. 핵심 API 점검

## 6. 파괴적 변경 원칙

예시:

- 컬럼 삭제
- 타입 변경
- 테이블 분리/병합

진행 방식:

1. 신규 컬럼/구조 추가
2. 애플리케이션 양쪽 구조 병행 지원
3. 데이터 이관
4. 구 구조 참조 제거
5. 이후 버전에서 구 컬럼 제거

## 7. 인덱스 전략

- 대량 데이터가 쌓이는 `print_requests`, `print_jobs`, `audit_logs`는 인덱스 변경 시 영향도 검토 필수
- 운영 중 인덱스 추가는 락 영향 검토 필요
- 조회 패턴이 확인된 뒤 복합 인덱스를 추가한다

## 8. 시드 데이터 전략

- `roles` 같은 기준 데이터는 seed로 관리
- 조직/사용자/프린터 예시 데이터는 개발 환경 전용으로 구분
- 운영 환경에는 샘플 데이터 반영 금지

권장 예시:

```text
db/
  seed.sql
  seeds/
    dev_seed.sql
    stage_seed.sql
```

## 9. 롤백 전략

원칙적으로는 `rollback SQL`보다는 `fix-forward`를 권장한다.

다만 아래는 별도 준비가 필요하다.

- 대형 데이터 이관
- 대규모 삭제
- 상태값 일괄 변경

운영 반영 전 준비 항목:

- DB 백업 여부
- 영향 테이블 목록
- 복구 소요 시간
- 긴급 연락 체계

## 10. 권장 다음 작업

1. `db/migrations` 폴더 생성
2. `schema.sql` 기준 초기 마이그레이션 파일 분리
3. 적용 순서 문서화
4. 향후 Prisma/TypeORM/Flyway 중 하나로 표준화 여부 결정
